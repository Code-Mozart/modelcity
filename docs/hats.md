| ^6 | decision | decided | **Through-node curve model:** nodes lie *on* the curve and each carries a heading. An edge between two nodes is one of: *bend* (straight, arc, straight; the arc's circle is tangent to both heading lines), *S-curve* (straight, arc, straight through the inflection point, arc, straight; both arcs share one radius), *hook* (same-direction two-arc edge, up to ~285 degrees; provisional, not designed). A single arc cannot exceed 180 degrees in the bend form. Source: handover section 2. See ^7, ^8. |
| ^7 | decision | decided | **Shape tag:** positions + headings + radius do not fully determine an edge (same data can be a bend or an S; a hook has a rotation direction). So each edge stores a shape tag (bend / S / hook, plus first turn direction). It is chosen automatically at creation and cleared when a heading is edited. If a stored tag stops being valid the edge falls back to automatic choice. Refines ^6. |
| ^8 | decision | decided | **Radius:** one per edge, either *auto* (the largest that fits) or explicit. Changing the radius never changes headings. Bend gesture: the circle tangent to both heading lines through the cursor, grabbed at the arc midpoint. S/hook gesture: drag along the radial direction; both arcs of an S share the radius. Double-click resets to auto. Minimum radius 0.5 m in the demo (defaults per road class: see handover, unverified). Refines ^6. |
| ^9 | decision | decided | **Handle vocabulary:** black dot = node (position); black arrow with ring = heading (arrow tip drags it); blue point = where the two heading lines meet (bend), dragging sets both headings; on an S it is the generated inflection point; orange ring = radius; turquoise = corners of the control polygon (S: display only; hook: drag sets radius). Overlay colors: purple curve, blue guides, red labels. The handover's wider color legend (gray committed, green creating, magenta modifying, blue selection, red invalid) is not yet applied. Handles keep a constant on-screen size at any zoom. See ^6, ^8. |
| ^10 | decision | decided | **Insert a node on a curve:** the new node takes the tangent as its heading and both halves keep the radius and a matching shape tag, so the curve does not change. See ^6, ^7, ^8. |
| ^11 | decision | decided | **Editing conventions (demo):** tools Move / Append / Insert (keys M, A, I); Append extends at the nearer end of the path, new heading chosen so the new edge is a single bend; right-click or Del removes a node; Esc returns to Move; Shift while dragging a heading snaps to 15 degrees; handles win over empty space, nodes win over other handles when the cursor is right on them. Handover conventions not yet ported: typed length/angle, 0.5 m click filter, guide snapping, one-road-one-undo. |
| ^12 | decision | decided | **Port architecture:** curve geometry is a pure, tested library in `src/lib/curves/` working in meters (the demo's 6 px = 1 m); the editor interaction engine is separate from the canvas component; the canvas component only dispatches input and draws. The demo stays as a reference. Builds on ^4. |

| ^14 | decision | superseded by ^30 (touch part still holds) | **Navigation vs editing input:** wheel/pinch zooms; dragging empty space or middle-button drag pans; dragging a handle edits. In Append/Insert tools a click acts, and panning needs the middle button. Space+drag was removed (did not work). Touch: one-finger on empty space pans. |
| ^15 | bug | fixed | While dragging a handle, the blue hover ring stayed at the point where the drag started. Fix: clear the hover when a drag starts. Reported by the user while testing ^13. |
| ^16 | bug | fixed | Nodes 1 (heading up) and 2 (heading east), whose heading lines meet in a proper corner, became an S-curve instead of an L (single bend). | ^17 | bug | fixed | Dragging the orange radius ring of an S-curve was inverted (toward the turquoise corner increased the radius). Cause: a linear radius-from-displacement rule with the wrong sign. | ^18 | question | open (minor) | User observed that the turquoise points are draggable on the hook preset but not on Fig G (S-curve). Proposal: draw display-only points differently (e.g. small hollow rings) so they do not look draggable. Awaiting user decision. |

| ^29 | decision | decided (principles) | **UI design principles:** minimal chrome, canvas (almost) full-screen; progressive disclosure (show tools, options and handles only when relevant, e.g. only for the selection or active tool); Fitts's law (frequent targets big and near the pointer, edges and corners are cheap targets); Hick's law (few choices at a time, group and hide the rest; the user wrote "Higgs law", read as Hick's); consistency with the handle vocabulary (^9) and keymap (^11); discoverability through hover hints rather than permanent legends. The current toolbar and legend of ^13 are provisional and will be replaced in ^20. |
| ^30 | decision | decided | **Camera and pointer controls (supersedes ^14, answers ^28).** Mouse: LMB drag = selection box (later; nothing yet on empty space); RMB drag = pan; MMB drag = rotate and precise zoom about the point where the drag started: horizontal movement rotates (right = clockwise), vertical movement zooms (up = zoom in), like Blender's Ctrl+MMB (revised by the user after testing; originally vertical movement changed the rotation sensitivity). Wheel = zoom at the cursor. While rotating: Esc cancels the rotation (restores the view from before the drag); N, E, S, W set the rotation so that north/east/south/west points up (N = reset); the cursor turns into a compass (needle points to world north) with N, E, S, W key chips, which can also be clicked (LMB while MMB is held); layout in ^33. Touch: two-finger twist rotates (about the finger midpoint), the same gesture also pinch-zooms and pans; one finger drags handles, or pans on empty space. The grid is pinned to the camera: it stays axis-aligned to the screen and does not move at all while rotating (it has its own center in the view, separate from the camera center, which moves when rotating about an off-center pivot); it only follows panning and zooming (revised after testing). |
| ^31 | decision | assumed | **Details I filled in for ^30:** (a) rotation is 0.4 degrees per horizontal pixel; (b) zoom is exponential, 1% per vertical pixel from the start of the drag (scale = scale at start x e^(0.01 x pixels moved up)), so returning to the starting height returns to the starting zoom; (f) a per-axis dead zone of 20 pixels around the drag start (8 at first, raised by the user after testing): horizontal movement within it does not rotate and vertical movement within it does not zoom, so a mostly vertical drag does not also rotate a little and vice versa; outside it the effect starts from zero (no jump), and after an N/E/S/W jump the dead zone is re-centered on the pointer. This recreates Blender's "Dolly" zoom style, where the zoom factor is 1 + (distance moved) x 0.01 per pixel, dragging up zooms in; the exact current Blender source could not be read (projects.blender.org is not reachable from this session), the exponential form matches it to first order and never degenerates; (c) a right click without movement still removes a node (kept from ^11), a right drag never does; (d) the compass only exists during the middle-button drag, there is no permanent rotation indicator yet; (e) the world rotation is stored in the view as `rot` radians, positive = clockwise on screen. |
| ^32 | decision | decided | **UI principles (user):** (1) always good contrast and readability (WCAG: 4.5:1 for text, 3:1 for graphics and component edges, in light and dark mode; guarded by `src/lib/contrast.test.ts`, so new color tokens must be added to its pair list); (2) think in components: reuse symbols, colors, styles and icons. The **KeyCap** component (`KeyCap.svelte`: raised cap with a thick bottom edge, turns blue and sinks in while the key is pressed) is the one look for every hotkey hint (toolbar, legend, compass) and for key-like drag hints. Icons live in `Icon.svelte`. Colors are CSS tokens in `app.css`, including text variants (`red-ink`, `orange-ink`) for labels. Extends ^29. |
| ^33 | decision | decided | **Compass layout while middle-dragging (revised by the user):** the compass sits at the cursor; fixed drag hints sit on the inner ring as plain monochrome icons in the compass outline color with no background: counterclockwise-rotation icon left, clockwise icon right, magnifying glass with + above (zoom in), magnifying glass with - below (zoom out; bare + and - read as add/remove rather than zoom, Claude's recommendation); N, E, S, W key caps sit on the outer ring in the on-screen direction of the real world direction (so they turn with the world, kept by the user), pressed (blue) while the key is held or the cap is clicked. |
| ^34 | decision | decided (visibility); assumed (2 s hold) | **Scale bar visibility:** the scale bar (bottom left) is only shown while it is useful: during a middle-button drag, and for 2 seconds after the last wheel zoom or pinch (the timer restarts with each zoom). Panning alone does not show it. |

| ^37 | decision | decided | **Camera bounds (user):** a bounding box is drawn around all control points and handles. The camera's viewbox must never leave it completely, and not even quite edge to edge: a few pixels of the bounding box area must always be on screen, so the user cannot get lost. Details: ^38. |
| ^38 | decision | assumed | **Details for ^37:** the box is axis-aligned in world coordinates and covers all nodes, blue points, orange rings and turquoise points plus a 48 px margin (screen pixels, which also covers the heading-arrow tips), so even a single node has an area. "A few pixels" = at least 12 px of the box on screen in every direction, at any rotation (the box is rotated with the view). When the view would leave, it is moved by the least amount needed. It is drawn as a thin dashed muted outline, so it is visible why the camera stops there. The box follows the content (dragging, inserting and deleting nodes change it, and the view is pulled back if the content moves away). With nothing drawn there is no box and only the old limits apply (view center within 2.5 km of the origin, ^2). |
